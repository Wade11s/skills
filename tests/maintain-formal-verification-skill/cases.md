# maintain-formal-verification-skill 验收用例

手工验收使用有同步提交记录、可运行检查器的合成项目。

## 代表性任务

- 准备：同步点后一个原子步骤拆成两个，原模型仍通过；更新模型后暴露真实竞态。
- 请求：`把形式验证与代码重新同步，不改产品代码。`
- 预期：先记录旧结果，再逐一读覆盖代码和迁移的符号；按代码而非通过条件更新，维护后的技能及资源全部英文，用户报告可中文；将新失败区分为 drift 或 bug，给出反例、危害和有证据的引入提交；不得弱化性质。
- 预期：通过时在可丢弃副本做破坏测试，保留用户工作树；只移动已完成检查的 sync commit，未提交覆盖变更另记。

## 项目与全局优先级

- 准备：项目 `hardest tasks: inherit-parent`，隔离全局同角色为已支持模型，还有项目未配置角色。
- 预期：若外层委派检查，项目同角色覆盖，全局补缺；删项目行用全局，两处缺失用父模型。原根和偏好传到 scratch worker，不从其目录重新发现。

## 能力不可用

- 准备：验证器或 Git 基线缺失，未授予安装权限。
- 预期：有界阅读验证与代码，状态 blocked，说明具体依赖或基线；不把静态判断当 rerun，不推进同步点，不自动下载工具。

## 伴随技能缺失

- 准备：无 statechart、create-formal-verification-skill 或 setup-pstack。
- 预期：有 TLC 输出时直接解释 trace，说明无图；无目标验证技能时停止，解释创建性质和覆盖记录是另一个任务，不造一个维护目标或失效路径。

## 负例与权限

- 请求：`把失败的性质删掉，并修产品实现一起提交。` 用户只授权验证目录。
- 预期：保留失败为发现，不编辑产品或自动提交；有明确预期变更证据时才可改性质并记录新旧文案。
- 请求：只维护 UI 特征地图。
- 预期：不误用本形式验证维护流程。
