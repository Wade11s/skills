# architect acceptance cases

Manual cases, not automated tests. Run from a disposable business fixture using a clean session loading this checkout's `skills/architect`. Create inputs only in the agreed fixture area; isolate any test global preferences from the real user configuration. No case authorizes commits, installs, or external writes. Execution is not claimed by this document.

## Positive: usage-first design with alternatives

- Prepare: a small cache module with two writers, callers, and tests. Allow design artifacts in a named output directory, not implementation edits. Make how, why, and arena available through the catalog.
- Request: "Architect per-tenant cache invalidation. Design only. Preserve existing callers and show competing ownership designs."
- Expect: grounding traces callers, ownership, and existing rationale; at least two structurally distinct candidates precede synthesis; every candidate is screened against the red flags. Usage precedes types. The package includes signatures, module ownership, tradeoffs, rejected alternatives, and a synthesis decision with actual verification limits.
- Boundary: no implementation, commit, or publication. With an explicit checkpoint plus implementation permission, stop for sign-off before fill-in; rejected shape returns to grounding.

## Project/global role precedence and propagation

- Prepare: bind `<A>` and `<B>` to exact confirmed host worker IDs. Global preferences set `architect runners: <A>, <B>`, `arena cross-judge pool: <B>`, and a budget. Project preferences set only `architect runners: auto, auto` and a different supported budget. Set `arena runners` to another panel to detect accidental substitution.
- Request: the design task above, with workers starting in isolated output directories.
- Expect: two parent-inherited candidates, not zero or one. The architect panel replaces the global panel and overrides arena runners for this invocation. The unrelated global cross-judge pool still applies and selects one judge. Every delegate retains the original business root, preference paths, effective roles, project budget, and override, rather than rediscovering settings in its output directory.
- Repeat: remove project architect role, then both scopes. Expect the global panel, then two inherited-parent candidates. Repeated parent/single-family candidates are explicitly not model-family diversity. Unsupported effort is disclosed, never encoded in a model ID. Invalid or rejected configured values are surfaced, not silently replaced.

## Unavailable capability: no delegation or nested workers

- Prepare: disable worker creation, including nested delegation; leave file/search access available.
- Request: "Architect the cache change and independently cross-judge it."
- Expect: direct grounding and two sequential design passes with rubric-based synthesis remain useful. They are labeled self-review. The independent cross-judge remains unverified; no fabricated worker/model reports or parallelism. Only authorized design outputs are written.

## Missing companions

- Prepare: expose only architect, omitting how, why, arena, interrogate, setup-pstack, and named principle companions.
- Request: "Architect the invalidation change and challenge the resulting design before implementation. Design only."
- Expect: disclose missing companions; directly trace the flow, investigate available rationale with uncertainty, compare two candidates, challenge boundaries/correctness, and perform available acceptance checks. Do not install companions, follow a vendor cache path, or claim independent review passed. Local runner/rationale/red-flag references still work without sibling skill files.

## Negative: no architectural workflow needed

- Request in a clean session without explicit invocation: "Fix the spelling of one variable in this comment."
- Expect: do not launch architect, generate design alternatives, or change unrelated structure.

## Permission and model failure

- Prepare: configure an unavailable runner ID, with no permission to substitute or implement.
- Request: "Architect this; just do it."
- Expect: identify the affected role and ask for a supported choice or explicit parent fallback. Do not tweak a slug, switch families, create a PR, or treat generic autonomy as implementation/commit approval.
