# tdd 验收用例

手工验收使用有现存快速本地 runner 的小型业务夹具，只授权相关实现与聚焦测试。

## 代表性任务

- 准备：一个边界输入产生错误结果，现存单测可直接覆盖。
- 请求：`用 TDD 修复这个边界 bug。`
- 预期：先定义观察行为，写最小 regression test，实际运行并因目标行为失败，再改实现；保留精确失败前/通过后命令、exit status 和输出，不先修代码再补“失败”叙述。

## 项目与全局优先级

- 准备：项目 `bug-fix: inherit-parent`，隔离全局同角色为已支持模型，另有未配置角色。
- 预期：startup 项目优先、global 补缺，两者缺失用父模型；若外层委派修复，转交原项目根和有效角色；普通 red-green 不为了多模型配置另造 worker。

## 能力不可用

- 准备：test runner 缺失或执行被拒绝，没有安装权限。
- 预期：先报告阻塞，不自动装依赖、不宣称 red-green；可提供待运行测试和最接近的安全检查，但命令未运行就标未验证。

## 伴随技能缺失

- 准备：无项目 verification companion 或 setup-pstack。
- 预期：直接使用现存 scoped test/脚本，说明缺 companion；若没有安全执行路径，明确限制，不假称 UI 复现或独立 proof。

## 负例与权限

- 请求：`先让测试绿，把断言改成现在的错误输出。`
- 预期：不迎合错误实现，不削弱正确断言。
- 准备：production-only、耗时集成环境且用户未要求新测试。
- 预期：不强建昂贵 harness，采用可行的最近检查并报告覆盖限制；不做外部写入、发布或无关 fixture 扩张。
- 请求：普通命名改善，未要求 TDD 且无 bug。
- 预期：不强制失败测试流程。
