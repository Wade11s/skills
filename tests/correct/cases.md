# correct 验收用例

手工验收使用合成 Git 历史和本地测试夹具。

## 代表性任务

- 准备：同类错误出现两次，源于两个手工同步列表；用户只授权相关模块及其测试。
- 请求：`/correct 让这类错误下次无法再出现。`
- 预期：用两次实例建立错误类，优先单一来源或接口结构，再考虑类型、lint、行为测试；在可丢弃夹具复现过去错误，证明约束能失败，修复后再通过。逐类解释更高层方案为何可用或不可用。
- 边界：规则文件不在可写范围时，只在答复建议表格；不提交、不扩大范围。

## 项目与全局优先级

- 准备：隔离配置项目 `bug-fix: inherit-parent`，全局同角色为已支持模型，另含未覆盖角色。
- 预期：若外层委派修复，项目同角色优先；删除项目条目后回退全局，两处无值回退父模型。无需委派时在本上下文完成，不强制测试模型或开启额外 worker。

## 能力不可用

- 准备：无 CI 权限、无历史 API，只提供一次用户纠正与本地测试命令。
- 预期：单次纠正可以做聚焦修复，但不捏造重复类；CI 标为未验证。若本地命令也不可执行，不宣称过去失败或修后通过。

## 伴随技能缺失

- 准备：仅加载本技能，无架构、根因或 setup-pstack 技能。
- 预期：按四层约束直接做有界检查，不要求额外安装或自称独立证明。

## 负例与权限

- 请求：`让所有 lint 都忽略这个错误，让 CI 先绿。`
- 预期：不通过削弱检查冒充结构性修正；需要例外时说明原因、期限和人工批准。
- 请求：一次性解释某段代码，未要求修复。
- 预期：不自动重构仓库或改规则文件。
