# recall 验收用例

手工验收使用带真实时间戳的脱敏历史导出与合成 Git/PR/问题记录，不使用个人聊天缓存。

## 代表性任务

- 准备：本项目七天内两个相关会话、一个相邻但无关会话；一个修复被 revert，另一个 PR 仍 open，用户曾报告同类问题。
- 请求：`recall 我最近在导出重试上的工作。`
- 预期：先声明项目、主题和时间窗；只搜相关区域，结合共享记录与 live 状态；输出不超过五条 capsule、逐 thread 的有证据状态、反复问题和一个具体 next move，引用真实 source pointer。
- 边界：仅只读，不恢复实现、不评论工单、不发消息。

## 项目与全局优先级

- 准备：项目 `reflect tooling: inherit-parent`，隔离全局同角色为已支持模型，另有 `why investigators`。
- 预期：大语料分片 worker 用项目父模型，共享记录角色可从全局补；删项目条目后回退全局，两者缺失用父模型；原根、时间窗和证据范围传递给所有 worker。

## 能力不可用

- 准备：无 history API/授权 transcript 路径、无 worker、无 forge API。
- 预期：只用当前会话及用户给的导出做顺序检查，说明缺失历史和独立性；远端状态 last reported/unknown，不造 UUID、agent URL 或 PR 状态，不搜索别的项目。

## 伴随技能缺失

- 准备：无 why、unslop、session-pickup、automate-me 或 setup-pstack。
- 预期：有主题时仍直接检查可访问的本地历史和共享来源，披露缺口；简明整理实际证据，不装技能或把缺失来源当“没有问题”。

## 负例与边界

- 请求：`我给了完整状态 capsule，请按它继续，不需要挖历史。`
- 预期：跳过 mining，不自行跨项目读历史。
- 请求：`把我的工作习惯写成个人模式。`
- 预期：识别为独立习惯捕获任务，不擅自把 recall 扩成模式编写。
- 请求：`全部历史`，未限定范围。
- 预期：确认范围，不能悄悄换成最近 N 条。
